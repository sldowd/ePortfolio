The Artifact

This artifact is Project Two, a client management application originally reverse engineered in CS-410 (Reverse Software Engineering) in C++ from a compiled binary file. The original version was structured around global scalar variables, had no separation between read and write access, accepted unvalidated integer input, and allowed unlimited login attempts. My CS-410 work refactored it into a two-class design (Customer/CustomerList), added input validation, and capped login attempts at three — but a formal vulnerability analysis from that course identified two further gaps that were documented but never implemented: the absence of password hashing/salting, and the absence of a role-based access control layer. This enhancement is where I closed both.

Why It Belongs in My ePortfolio and How It Was Improved

I selected this artifact because it lets the enhancement demonstrate a language-level security decision rather than a series of individual patches. Instead of fixing memory-safety issues in C++ one at a time, I ported the entire application to Rust, whose ownership and borrowing model enforces memory safety at compile time — closing an entire vulnerability class rather than specific instances of it.

Specific improvements: I replaced the two previously unimplemented gaps directly. A Role enum (Admin/Viewer) and a gate on every mutating operation means only an authenticated Admin can change a customer's service — Viewers can read but not write, enforced by the type system rather than a convention a future developer could forget to check. The original program checked only the shared password and never looked at the username. The rewritten version finds the account first. If the username doesn’t exist, the program still runs an Argon2 verification against a dummy hash, then returns the same “Invalid username or password” message used for a wrong password. Response time is therefore about the same either way, so an attacker can’t tell which usernames exist by timing the response. The single hardcoded plaintext password ("123", shared by every user) is gone; each user now has an individually Argon2id-hashed credential, verified by the Argon2 library, which compares hashes in constant time instead of comparing plaintext the way the original's .compare() call did. I also replaced the original’s 1/2 magic-number service codes with a ServiceType enum. Once a value is a ServiceType, it can only be Brokerage or Retirement, so code that uses it can’t carry an invalid service. The raw number a user types still must be checked at runtime. ServiceType::from_int converts it and returns an error for anything other than 1 or 2, and Rust requires the caller to handle that result.

Course Outcomes

I met Course Outcome 3 (evaluating trade-offs in design choices) — the decision to do a full rewrite instead of incremental patching is explicit, not incidental, and I can point to the specific vulnerability classes it closes. I met Course Outcome 4 (well-founded, innovative techniques) through the migration itself, particularly using Result<T, E> for fallible operations in place of C++ exceptions, which changes how errors propagate through the program, not just how they're named. Course Outcome 5 runs through the whole enhancement, since every change — the RBAC gate, the hashing, the enum-enforced service type — is a security decision.

One update to the original plan: my Module One proposal named password hashing and RBAC as the two gaps to close, but didn't separately call out that the original's single shared password meant there was no real per-user identity at all, only a shared secret. I treated that as in-scope alongside hashing, since Argon2id on a single shared password would have been a hashed version of the same underlying problem. I explicitly did not implement true account lockout/rate-limiting after failed attempts — that's a deliberate scope decision, documented here rather than an oversight, made in the interest of finishing the two higher-value fixes given the time available for this enhancement.

Feedback: included adding automated security tests for authorization boundaries and credential verification. A test suite is included with the rust port.

Outcomes not fully met: I did not implement account lockout or rate limiting after failed login attempts, so the program still allows repeated guessing beyond the three-attempt cap. The admin credential is also still a hardcoded hash in the source code, a known risk I would address before any production use.

Reflection

This was my first substantial project in Rust, and the challenges tracked pretty directly onto core language concepts rather than surface syntax. I hit repeated errors around the difference between &self and &mut self before the read/mutate distinction actually clicked; the difference between a type name and a constructed value (Vec<Customer> versus Vec::new()); why Result propagation via ? can't silently convert between unrelated error types; and why a function's last line determines its return value only when it isn't terminated with a semicolon. None of these are C++ concepts with a direct analog — they're closer to the compiler enforcing invariants that C++ would have quietly let me violate (returning a reference to data that's already been freed, for instance, which C++ permits as a dangling pointer and Rust refuses to compile).

I also ran into a live dependency issue mid-implementation: adding the argon2 crate pulled its newest version, which had changed its password-hashing API in a way that broke every reference example I had, including ones from the crate's own documentation history. Resolving it meant learning to pin an exact crate version rather than assume "latest" is safe to add mid-project — a small but real lesson about dependency management that C++'s compile-and-link model doesn't really have an equivalent to.

I used Claude throughout this process as a debugging partner — explaining compiler errors as I hit them, reviewing my own attempts at each method before I moved on, and helping me understand why something didn't compile rather than just supplying a fix — consistent with SNHU's generative AI usage guidelines, which I'm acknowledging here per that policy.
