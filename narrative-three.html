The Artifact

The artifact is the Grazioso Salvare dashboard and its data-access module, a full-stack Python application that helps identify rescue-dog candidates from Austin Animal Center shelter data. It uses MongoDB for storage (10,000 records), PyMongo for database access, and a Dash web dashboard for display. I originally built it in CS-340. The part I enhanced for this category is animal_shelter.py, the class that wraps create, read, update, and delete operations against the MongoDB collection.

Why It Belongs in My ePortfolio and How It Was Improved

I chose this artifact because the data-access layer is where an application meets its database, so it is the natural place to show database skills and a security mindset together. That combination matches the security-focused roles I am targeting. In its original form the module passed whatever query dictionary it received straight to PyMongo. The dashboard has no free-text input today, but the module is reusable, and any future caller could send it a hostile query.

I added a validation and access-control layer. Queries are checked against an allow-list of field names, value types, and operators before they reach the database, so operators such as $where and $regex are rejected. Documents are validated on create and update for field names, types, length, and required fields. Update and delete refuse an empty filter, and accept only exact-match operators, so one bad call cannot erase the collection. Failures now raise clear exceptions (ValidationError, DatabaseError, PermissionError) instead of being printed and converted into an empty list or zero. The connection is verified with a ping at startup, and credentials are URL-escaped and never appear in error messages. I also added a read-only mode, which the dashboard now uses, and a script that creates a least-privilege read-only database user. The result of the validation is easy to see:

{'breed': 'Labrador Retriever Mix'} -> accepted
{'$where': 'sleep(5000)'} -> rejected ($where)
{'breed': {'$ne': None}} -> rejected (NoneType)
{'breed': {'$regex': '.*'}} -> rejected ($regex)

I wrote 23 unit tests that confirm both the legitimate and malicious cases. Each rejection test also checks that nothing reached the database.

Course Outcomes

I met the outcomes I planned in Module One. Outcome 4 is shown by the database techniques (validation, least-privilege roles, connection handling), and Outcome 5 by anticipating injection and misuse at the data layer. Outcome 3 is shown by the trade-offs: a stricter query interface protects the database but breaks callers that send unusual queries, so I documented the behavior change and kept the dashboard's own queries valid. Outcome 2 is addressed by this narrative and the README documentation. I have two updates to my plan. First, I planned to block a list of dangerous operators, but I implemented an allow-list instead, because a block-list fails the moment a new dangerous operator exists. Second, I added the read-only mode and database-level user, which were not in my original plan.

Outcome not fully met: My unit tests use an in-memory stand-in for the collection, so the database interaction has not been tested against a live MongoDB instance. The validation logic is verified, but its behavior against the real database is not.

Reflection

The most important lesson was that validation and permissions protect different things. The allow-list stops malicious queries, and the read-only database user limits the damage if something gets through, so each layer covers the other's failure. My own testing reinforced this. My first version allowed operators like $ne on delete, and a test showed that delete({"animal_id": {"$ne": ""}}) would match nearly every record and defeat my empty-filter guard. I fixed it by limiting update and delete to exact-match operators. I also learned that the original connection error handling never worked, because MongoClient connects lazily and the try/except could never catch a failed connection. The original also hid failures by returning empty results, so a broken database looked the same as a search with no matches.

The main challenge was my development environment. Setting up MongoDB on the 2014 Intel iMac I’m using took longer than the coding, because Homebrew no longer supports intel macs, and I’m currently running the most recent OS via OpenCore Legacy Patcher. I eventually installed MongoDB directly and learned how authentication and the authSource option work. Because of this, my unit tests use an in-memory stand-in for the collection instead of a live server. They verify the validation logic, but they do not replace testing against a real MongoDB instance.

I used Claude throughout this process as a debugging partner, explaining errors as I hit them and reviewing my own approaches before moving on. I acknowledge that use here, consistent with SNHU's generative AI usage guidelines.
