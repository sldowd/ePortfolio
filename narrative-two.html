The Artifact

The artifact is the Grazioso Salvare Dashboard, a Python/Dash web application backed by MongoDB (dashboard.py, animal_shelter.py). I built it in CS-340 (Client/Server Development) in late 2025 to help a fictional rescue-training company find rescue dog candidates among 10,000 Austin Animal Center outcome records. In its original form, each of the three rescue profiles was an exact-match MongoDB query: breed in a fixed list, one required sex, and a hard age range. A dog that failed any single condition was excluded entirely.

I chose this artifact because it's the project where an algorithm design decision directly changes what the user sees. I replaced the pass/fail queries with a weighted scoring algorithm (scoring_algorithm.py): breed is worth 40 points, sex 30, and age 30, with age earning partial credit that drops one point per week outside the ideal range. Profile criteria live in a rescue_profiles dictionary, so a new profile is a data change, not a code change. The dashboard now fetches all records, scores each against the selected profile, hides anything below a MIN_SCORE of 70, and ranks the rest in a new Fit Score column.

Choosing the weights. Breed carries the most weight (40 points) because each rescue profile is built around a specific set of breeds, and a dog outside that set doesn’t fit the training goal. Sex and age share the remaining 60 points at 30 each. Age gets partial credit outside the range, so a dog that is a few weeks past the bound stays in the ranking instead of disappearing. The 70-point cutoff means a dog needs a preferred breed plus at least one other criterion to appear.

These weights are a judgment, not a measured result. Outcome data would test them: if records showed which dogs completed training, I could check whether breed, sex, or age predicts success, and adjust the weights to match.

Feedback asked me to justify the weights, so this section explains the reasoning behind each value.

The MIN_SCORE cutoff wasn't in my original plan. I added it when I realized the breed chart, age chart, and map all read from the table's data, so ranking every animal in the shelter would have made them describe the whole shelter instead of the matches.

Time Trade-Off

The old approach filtered inside MongoDB, so only matching records reached the application. The new approach fetches all records per selection and scores them in Python, which is O(n) for scoring plus O(m log m) to sort the m animals above the cutoff. I originally described the old filter as O(1) and corrected that: it's O(n) as a collection scan, or roughly O(log n + k) with an index. The extra cost turned out to be negligible. Scoring 10,000 records takes only 12-18 milliseconds, while the strict query was fast but so selective that there was almost nothing to rank. Spending milliseconds to go from 4 candidates to 30 is a clear win at this scale. At much larger scale, the scoring could move into a MongoDB aggregation pipeline.

Process and Challenges

The algorithm took less time than getting an environment that could run it. I spent roughly three hours across two days on environment problems, more than on the algorithm itself.

Virtual environment: My project sat in an iCloud-synced folder, and importing NumPy stalled. I moved the project out of the synced folder, rebuilt the venv, and resolved a dependency conflict: requirements.txt pinned Flask==3.1.0 while Dash 2.18.2 requires Flask<3.1.

Authentication: My script failed with a confusing pandas error. The real cause was upstream: read() caught an "Authentication failed" exception, printed it, and returned an empty list, which became a DataFrame with no columns. The root causes were a fresh local MongoDB with no data and no user, plus a connection string that authenticated against admin by default. I imported the data, created the user, and added authSource to the URI in animal_shelter.py.

Homebrew: brew services failed in several ways, and brew upgrade began compiling dependencies from source. Homebrew's own output explained why: Intel Macs are now an unsupported tier that no longer gets prebuilt packages. I couldn't tie the service failure to one confirmed cause, but the pattern showed Homebrew was no longer a reliable way to manage MongoDB on my machine. I stopped repairing it and switched to MongoDB's official downloads: the Community Server tarball, a standalone mongosh (Homebrew's copy had also broken), and a manually started mongod.

Lessons

Separate environment failures from code failures early. An error handler that returns an empty result can hide the real cause far from where it surfaces. And set a time limit on repairing a tool, then switch to a different path.
